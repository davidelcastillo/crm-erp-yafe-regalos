# Aislar la base de datos de tests y desarrollo

Objetivo: que los tests que escriben en base corran contra un stack local desechable y nunca contra un proyecto remoto.
Rama: `chore/odd-adoption-cleanup` · Entrega: `auto-chain`, `feature-branch-chain`; solo commits locales · Runner: `npm test` (Jest) y el stack local de Supabase en Docker.

## Specs

- **S1**: «Mejora 2 — Aislar la base de tests y desarrollo» con el motivo registrado: «Un test (`branchAdminService.test.ts`) pega a una base real y no hay `prisma/migrations`: correr la suite puede escribir donde no debe». Los tests que escriben en base **deben** usar una base local y desechable; ningún comando de este plan puede apuntar a un proyecto remoto.
- **S2**: Estrategia elegida por el usuario: «Stack local de Supabase en Docker (recomendado)» — «`supabase init` + `supabase start` con Docker (ya tenés 29.8.2): base desechable y reproducible, sin tocar producción». La configuración del stack **debe** quedar versionada y arrancar con un comando documentado.
- **S3**: Correr la suite contra la base local **no debe** exigir editar código de la aplicación ni recordar una URL de memoria: debe existir un comando portable que fije la conexión local.
- **S4**: El esquema **debe** poder aplicarse a la base local de forma reproducible; hoy no hay `prisma/migrations`, así que la reproducción se documenta con lo que sí existe.
- **S5**: Si la base local no está levantada, el comando **debe** fallar de forma explícita, sin caer silenciosamente en otra conexión.
- **S6**: Documentación afectada actualizada en el mismo PR: `AGENTS.md` (§2 entorno), `docs/README.md` y `.env.example`.
- **S7**: Verificación observada: stack arriba, esquema aplicado y la suite que toca base ejecutada contra el local; nada contra el remoto. Cambio de entorno → verificación independiente al cerrar.

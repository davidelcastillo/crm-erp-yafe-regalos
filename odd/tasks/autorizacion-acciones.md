# Autorización admin dentro de las Server Actions internas

Objetivo: que cada Server Action interna verifique sesión + rol `admin` dentro de la acción (no solo en el proxy y la UI), fallando cerrado.
Rama: `feat/auth-guard-acciones`, encadenada sobre `feat/etiquetas-ronda-2` (HEAD `8b7a43c`), que a su vez sale de `main` (`81d303c`). Entrega: commits locales por unidad, sin push ni PR. Runner: `npm test` (el guardián se mockea como autorizado en `jest.setup.ts`, así que las suites no necesitan Supabase).

## Specs

- **S1** — Regla del proyecto, `AGENTS.md` §0.2, verbatim: «Rutas internas: sesión + rol `admin`. Una redirección del proxy **no** autoriza una mutación.» Cada Server Action interna debe comprobar la sesión y el rol **dentro** de la acción, porque es la única frontera que un cliente puede llamar directamente.
- **S2** — Hallazgo que abre la unidad (`odd/tasks/etiquetas-precios.md`, L11, verificación independiente), verbatim: «`generateProductLabels` y `getBranchProductsForExport` no verifican sesión/rol **dentro** de la acción (igual que el resto de `src/app/actions/`; solo `branch.ts` lo hace): la protección es proxy + UI. Es lectura de precios y stock, no mutación; arreglarlo es una unidad transversal de auth, no de esta ronda.»
- **S3** — Decisión del usuario, verbatim: opción «**Todas las acciones internas (~45)**», cuya descripción dice: «`requireAdmin()` al inicio de cada acción exportada de los 9 módulos, con el catálogo público afuera. Documento ODD, RED→GREEN por módulo y checks. Es la deuda completa que reportó el verificador.»
- **S4** — Falla cerrado. Devuelve `{ success: false, error: "No autorizado" }` —el mismo texto que ya usaba `branch.ts`— cuando: no hay sesión, el rol de `app_metadata` no es `admin`, el claim falta, o el cliente de Supabase lanza. Nunca degrada a permitir.
- **S5** — Orden y efecto cero. El guardián corre **antes** de Zod y **antes** de cualquier consulta o escritura de Prisma: un rechazo no valida, no lee y no escribe. El test lo fija con `not.toHaveBeenCalled()` sobre los mocks de Prisma.
- **S6** — Fuera de alcance. (a) El catálogo público `src/app/actions/inventory.external.ts` queda sin guardián: es de solo lectura y `isActive && isPublic` lo decide la propia acción. (b) `src/actions/auth.ts` (login/logout) queda afuera. (c) No cambian reglas de negocio, validaciones, firmas de retorno ni la navegación del proxy; no se agregan dependencias ni cambios de esquema.
- **S7** — Verificación observada. RED y GREEN por módulo, suite completa, `npx tsc --noEmit`, `npm run lint` y `npm run build`. Toca permisos/auth: **riesgo item 2**, con verificación independiente antes del cierre.
- **S8** — Decisión del usuario del 2026-10-21, verbatim: «Test parametrizado para las 59 (recomendado)», sobre la pregunta de cómo cerrar la cobertura de rechazo de las 48 acciones sin caso propio. Cada acción interna, llamada con una sesión que no es `admin`, debe devolver «No autorizado» —no un error de validación ni de Prisma—, y la cobertura no puede depender de mantener una lista a mano.
- **S9** — Decisión del usuario del 2026-10-21, verbatim: «Mantener el error (recomendado)» para `getBranchOptions` sin sesión admin. No se vuelve a `{ success: true, data: [] }`: devolver datos vacíos ante una sesión ausente oculta el problema, y sus tres consumidores ya toleran el fallo.

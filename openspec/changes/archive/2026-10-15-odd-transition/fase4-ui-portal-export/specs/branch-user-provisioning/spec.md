# Branch User Provisioning Specification

## Purpose

Automatically provision and deprovision Supabase Auth users for branches. A branch user authenticates into the same Supabase project and carries custom claims `{ role: 'branch_user', branchId }` in `app_metadata`, used by middleware for portal and admin access control.

## Requirements

### Requirement: Service Client

The system MUST provide `createServiceClient()` building a Supabase client with `SUPABASE_SERVICE_ROLE_KEY`. The client MUST only be used server-side and MUST be able to call `auth.admin` APIs.

#### Scenario: Service client available
- GIVEN SUPABASE_SERVICE_ROLE_KEY is defined in the environment
- WHEN calling createServiceClient()
- THEN an admin-capable Supabase client SHALL be returned

### Requirement: Create Branch User

The system MUST provide `createBranchUser(branch)` that creates an Auth user with email derived from the branch code, a temporary password of at least 12 characters covering 4 character classes, `email_confirm: true`, and `app_metadata: { role: 'branch_user', branchId }`. The password MUST be generated by `generateTemporaryPassword()` and MUST NOT be persisted anywhere.

#### Scenario: Create user with claims
- GIVEN a branch with code "CEN"
- WHEN calling createBranchUser
- THEN an Auth user SHALL exist with email sucursal-cen@... and app_metadata { role: 'branch_user', branchId }
- AND the email SHALL be confirmed

#### Scenario: Temporary password meets policy
- GIVEN generateTemporaryPassword()
- THEN the password SHALL be at least 12 characters
- AND SHALL include lowercase, uppercase, digit, and symbol classes

### Requirement: Delete Branch User

The system MUST provide `deleteBranchUser(userId)` that deletes the Auth user and SHALL propagate failure to the caller.

#### Scenario: Delete user succeeds
- GIVEN an existing branch user
- WHEN calling deleteBranchUser
- THEN the Auth user SHALL be removed

### Requirement: Admin Route Gating

The system MUST gate internal admin routes in `src/middleware.ts` by role claim: only sessions with role `admin` SHALL pass. Sessions without the claim SHALL be rejected. The `admin` claim MUST be backfilled to the existing admin user before strict gating activates.

#### Scenario: Admin claim allows access
- GIVEN a session with app_metadata role "admin"
- WHEN requesting an internal admin route
- THEN the request SHALL proceed

#### Scenario: Missing claim rejected
- GIVEN a session without role claim
- WHEN requesting an internal admin route
- THEN the request SHALL be rejected
